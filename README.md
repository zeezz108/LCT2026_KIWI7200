# Обнаружение препятствий перед беспилотным поездом метро по данным 3D‑лидара

Решение кейса «Московский транспорт», ЛЦТ 2026.

ROS 2‑узел на C++ получает облако точек лидара и отвечает на вопрос «**Путь свободен?**». Выход — одно из трёх состояний:
- **CLEAR** — путь свободен на X м;
- **WARNING** — рядом с путём объект;
- **DANGER** — препятствие внутри габарита поезда на расстоянии X м, тормозить.

Для каждого объекта выдаются расстояние вдоль пути, боковое смещение, размер, скорость сближения и время до столкновения.

Алгоритм не распознаёт классы объектов. Он опирается на то, что свойственно самому тоннелю:
- поезд едет по **рельсам** — они задают ось пути вблизи;
- **габарит поезда проходит сквозь тоннель, не задевая стен, а стены идут параллельно пути** — это задаёт изгиб и уклон пути вдали;
- всё, что оказалось внутри этого движущегося габарита, возвышается над полотном и держится несколько кадров, — препятствие.

Обучающие примеры препятствий не нужны, поэтому решение переносится на незнакомые участки: круглые и прямоугольные тоннели, двухпутные, станции, стрелки, гермозатворы.

**Результаты** на записях кейса и синтетических препятствиях ([docs/experiments.md](docs/experiments.md)):

| | |
|---|---|
| Ложные ОПАСНОСТИ / ВНИМАНИЯ, **13 558 кадров** без препятствий | **0.15% / 3.02%** кадров; все 21 ложный кадр — конструкции под сводом и детали пути на дальности, где ось уже экстраполируется |
| Человек на пути в `doubleT_obstacle` (~56 м) | ОПАСНОСТЬ ровно пока он в габарите — кадры 10–105 без пропусков |
| Непрерывный проезд 20 минут (11 271 кадр, незнакомые тоннели) | ось по рельсам в 100% кадров, 21 ложная ОПАСНОСТЬ |
| **Объект на рельсах там же** (0.3 × 0.3 м, в 0.80 м от оси) | 77 кадров из 95 после ухода человека (было 31 из 101) |
| **Оборванный кабель в габарите** (требование заказчика) | петля на 40 м — 100% кадров, трос поперёк на 30 м — 86–91% |
| **Минимальный объект 300 × 300 × 100 мм** (основной критерий заказчика) | сообщается с 12 до 25 м уровнем ВНИМАНИЕ: на 20 м — 86% кадров в круглом тоннеле и на кривой, 36–59% на станции и в прямоугольном |
| Человек на оси пути, синтетика | 100% до 125 м, 91–100% на 150 м; в 1.0 м от оси (край габарита) — 100% на 50 м |
| Почему не дальше 150 м | в цель на 175 м попадает 3 различимых луча, а **путь в записях заказчика виден в среднем на 87 м и ни разу дальше 140 м** — разбор в [§ 5.4](docs/experiments.md) |
| Лежащий человек (0.35 м) | 100% кадров до 25 м; на 50 м — от 14% (кривая) до 100% (стрелка) в зависимости от участка |
| Ошибка профиля полотна против видимого пола | p90 0.15 м на 20–40 м, 0.23 м на 80–110 м |
| Ошибка оси против пройденного пути | 0.05 м до 30 м, 0.21 м на 100 м (медиана); на незнакомых тоннелях — 0.11 м на 100 м |
| Сближение с 200 м на 15 м/с | первая ОПАСНОСТЬ на 141 м (на кривой — на 85 м, дальше не видно) |
| Время кадра (Ryzen 5 5600, 4 потока) | 23 мс (±50°, 307 тыс. точек), 28 мс (360°, 921 тыс.); на одном ядре 24 и 29 мс |
| **Обобщение**: 12 изменённых условий съёмки (крепление, наклон, 64 канала, неорганизованное облако, потеря кадров, шум) | **ноль ложных тревог**, препятствие найдено во всех |

## Быстрый старт (Docker)

Требования: Ubuntu 22.04, Docker (плюс docker compose plugin для варианта с compose). Для RViz2 нужен X‑сервер.

```bash
# 1. сборка образа (внутри: colcon build + 39 тестов; с нуля, --no-cache: 1 мин 18 с на Ryzen 5 5600)
docker build -t tunnel-obstacle-detector -f docker/Dockerfile .

# 2. запуск детектора (сеть и IPC хоста — для DDS)
docker run --rm -it --net=host --ipc=host tunnel-obstacle-detector

# 3. в другом терминале — проигрывание бэга (на хосте с ROS 2 Humble или в том же образе)
ros2 bag play /path/to/doubleT_obstacle
# или без ROS на хосте:
docker run --rm -it --net=host --ipc=host -v /path/to/bags:/data:ro tunnel-obstacle-detector \
    ros2 bag play /data/doubleT_obstacle
```

> **Пользователь контейнера.** Облака (8–24 МБ на кадр) DDS передаёт через общую память `/dev/shm`. Процессы разных пользователей её не делят: детектор увидит топик, но кадров не получит. Образ по умолчанию работает от UID 1000 — обычного пользователя Ubuntu. Если `ros2 bag play` на хосте запускается другим пользователем, добавьте `--user $(id -u):$(id -g)`, если от root — `--user root`. Если после запусков от root данные не идут, удалите старые сегменты: `sudo rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps_*`.

Детектор сам находит первый топик `sensor_msgs/PointCloud2`: в данных это `/lidar_points` или `/sensing/lidar/hesai128/pointcloud`. Раз в секунду он печатает строку состояния:

```
[DANGER ] obstacle at 55.8 m | objects=1 free=56 m v=44 km/h | 10.0 fps proc p50=24.5 p95=30.6 ms (convert 2.3 + algo 21.9 + publish 0.1) transport=10.1 ms | lidar h=1.74 m axis=rails
```

### Демонстрация с RViz2 одной командой

```bash
xhost +local:docker                                   # разрешить окна из контейнера
BAG_DIR=/path/to/bags BAG=doubleT_obstacle docker compose --profile demo up --build
```

Поднимаются три сервиса: `detector`, `rviz` (конфиг `rviz/detector.rviz`) и `player` (бэг по кругу).

В RViz2 видно:
- облако, раскрашенное по зонам (синий — вне зон, ВНИМАНИЕ, красный — ОПАСНОСТЬ);
- ось пути и границы габарита, сечения габарита каждые 25 м;
- зелёную линию «путь свободен на X м»;
- боксы объектов с подписью расстояния и баннер статуса.

## Запуск без Docker (ROS 2 Humble)

```bash
mkdir -p ~/ws/src && cp -r ros2_ws/src/* ~/ws/src/ && cd ~/ws
source /opt/ros/humble/setup.bash
rosdep install --from-paths src --ignore-src -y     # rclcpp, vision_msgs, tf2_ros, rosbag2, eigen
colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash

# детектор + RViz2 + проигрывание бэга
ros2 launch tunnel_obstacle_detector detector.launch.py rviz:=true bag:=/path/to/doubleT_obstacle loop:=true
# только детектор; явный топик и лог CSV
ros2 launch tunnel_obstacle_detector detector.launch.py input_topic:=/lidar_points csv_log_path:=/tmp/log.csv

# тесты: 37 юнит-тестов ядра на синтетическом тоннеле + 2 теста самого ROS-узла (топик -> вердикт)
colcon test --packages-select tunnel_obstacle_detector && colcon test-result --verbose
```

### Офлайн‑обработка бэга (быстрее реального времени)

## Выход

| Топик | Тип | Что внутри |
|---|---|---|
| `/tunnel_obstacle_detector/status` | `tunnel_obstacle_msgs/ObstacleStatus` | `level` (0 CLEAR, 1 WARNING, 2 DANGER), `obstacle_detected`, `nearest_distance` (вдоль пути), `nearest_lateral`, `time_to_collision`, `confidence`, `free_distance`, `obstacles[]`, диагностика: время обработки, задержка передачи, высота/тангаж/крен лидара, кривизна пути, захват оси по рельсам |
| `/tunnel_obstacle_detector/obstacles` | `vision_msgs/Detection3DArray` | 3D‑боксы подтверждённых объектов, класс `danger`/`warning`, score |
| `/tunnel_obstacle_detector/markers` | `visualization_msgs/MarkerArray` | Визуализация для RViz2 |
| `/tunnel_obstacle_detector/view_points` | `sensor_msgs/PointCloud2` | Прореженное облако с каналом `zone` |
| `/tunnel_obstacle_detector/obstacle_points` | `sensor_msgs/PointCloud2` | Точки объектов |
| TF `track → <кадр лидара>` | static | Кадр пути по автокалибровке: X вдоль пути, Z от полотна |

```bash
ros2 topic echo /tunnel_obstacle_detector/status --field level
```

### Куда смотреть, чтобы проверить решение

Главный ответ — **одно поле `level` в `/tunnel_obstacle_detector/status`, по одному сообщению на каждый кадр лидара**:
0 — путь свободен, 1 — объект рядом с габаритом, 2 — препятствие в габарите. Дистанция до ближайшего препятствия —
`nearest_distance`. Всё остальное в сообщении справочное.

Если смотреть топики неудобно, детектор пишет два файла (пути задаются параметрами, в `docker compose` они уже
включены и попадают в `./results/`):

| файл | что внутри |
|---|---|
| `csv_log_path` → `detector_log.csv` | строка на каждый кадр: время, уровень, дистанция, смещение, TTC, уверенность, свободная длина пути, число объектов, время обработки, высота/тангаж/крен лидара |
| `summary_path` → `detector_summary.json` | итог прогона: сколько кадров, сколько из них CLEAR/WARNING/DANGER, время обработки p50/p95 и **список всех объектов**: с какой дистанции увиден, ближайшая дистанция, смещение от оси, высота, сколько кадров держался |

Пример сводки живого узла на записи с препятствиями (`doubleT_obstacle`, 20 с, 360° облако):

```json
{ "frames": 167, "frames_clear": 6, "frames_warning": 7, "frames_danger": 154,
  "processing_ms_p50": 27.4, "processing_ms_p95": 30.1, "train_speed_kmh_median": 0.0,
  "input_topic": "/sensing/lidar/hesai128/pointcloud",
  "objects": [
    {"id": 1, "level": "DANGER",  "frames":  66, "seen_from_m": 55.4, "nearest_m": 55.4, "lateral_m":  1.79, "height_m": 1.71, "max_points": 86, "seconds":  7.5},
    {"id": 2, "level": "DANGER",  "frames": 118, "seen_from_m": 56.4, "nearest_m": 55.9, "lateral_m": -0.90, "height_m": 0.54, "max_points": 11, "seconds": 15.2},
    {"id": 4, "level": "WARNING", "frames":   7, "seen_from_m": 54.8, "nearest_m": 54.7, "lateral_m":  1.90, "height_m": 1.52, "max_points":  8, "seconds":  1.2} ] }
```

Скорость нулевая, потому что в этой записи поезд стоит; на записи с движением тот же узел показывает
46.2 км/ч — она меряется по одному лидару, без одометрии (§ 4 [experiments.md](docs/experiments.md)).

Объект 1 — человек на пути, объект 2 — предмет на рельсах (он виден все 15 секунд, пока человек уходит и
возвращается). Кадров здесь 167, а не 201: узел считает те кадры, которые до него дошли от проигрывателя. Офлайн‑
прогон (`ros2 run tunnel_obstacle_detector offline_runner`) обрабатывает все 201.

Здесь `id 1` — человек на пути, `id 3` — предмет, лежащий на рельсах рядом с ним (0.49 м высотой, 8 возвратов),
`id 7` — второй человек в междупутье: он вне габарита, поэтому ВНИМАНИЕ, а не ОПАСНОСТЬ.

## Параметры

Все параметры с комментариями лежат в [`config/detector.yaml`](ros2_ws/src/tunnel_obstacle_detector/config/detector.yaml). Основные:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `input_topic` | `""` | Топик облака; пусто — первый найденный PointCloud2 |
| `sensor.forward_axis` | `-y` | Какая ось облака смотрит вперёд по ходу поезда (`x`, `-x`, `y`, `-y`) или `auto` — определить по первым кадрам |
| `calibration.fixed` | `false` | Поза лидара (высота, тангаж, крен) оценивается по полотну на лету; `true` — брать `fixed_*` |
| `zone.half_width_upper` / `lower` | 1.35 / 1.10 м | Полуширина габарита выше / ниже 0.9 м (внизу уже — контактный рельс) |
| `zone.bottom`, `zone.top` | 0.30 / 2.9 м | Высота зоны над полотном |
| `zone.warning_margin` / `warning_max_distance` | 1.0 м / 60 м | Ширина полосы ВНИМАНИЯ вокруг габарита и до какой дальности она проверяется |
| `corridor.length` | 200 м | Длина коридора |
| `detection.object_height_*` | см. yaml | Насколько объект должен возвышаться над видимым полом |
| `tracking.confirm_hits` / `confirm_window` | 3 / 5 | Подтверждение по кадрам (вдали требуется больше) |

## Эксперименты

- `scripts/run_offline_all.sh` — офлайн‑прогон всех бэгов → `data/results/*.jsonl`.
- `tools/inject_obstacles.py` — синтетическое препятствие (человек, ящики) в реальный бэг методом трассировки лучей лидара + эталон.
- `tools/evaluate_synthetic.py` — серия сценариев (дальность, боковое смещение, сближение на 15 м/с) → доля обнаружений, первая дистанция обнаружения, ложные тревоги.
- `tools/plot_debug_frame.py` — кадр с осью, габаритом, кластерами, причинами их отбраковки и картами конструкций.
- `tools/benchmark.py` — одна команда: ложные тревоги, время, синтетика; `--baseline <tag>` показывает разницу с прошлой конфигурацией.
- `tools/ego_motion.py` — восстановление движения поезда по кадрам лидара; пройденный путь служит эталоном оси.
- `tools/axis_error.py` — ошибка оси пути против пройденного пути, по дистанциям.
- `tools/fp_summary.py`, `tools/plot_experiments.py` — сводка ложных тревог и графики для `docs/experiments.md`.
- `tools/robustness.py` — 12 изменённых условий съёмки (крепление, наклон, 64 канала, неорганизованное облако, потеря кадров, шум) через `tools/transform_bag.py`.
- `tools/sensor_check.py` — модель сенсора против паспорта Pandar128E3X; `tools/profile_error.py` — ошибка профиля полотна против видимого пола.
- `tools/cut_parts.py` — короткий бэг из нескольких файлов длинной сплит-записи; `tools/summarize_run.py` — эпизоды тревог на длинном проезде.
- `tools/accumulation_probe.py` — сколько возвратов накапливается на объекте, если сложить несколько кадров (разбор дальности, § 5.4).
- `scripts/timing_scaling.sh` — время кадра при 1/2/4/6 потоках OpenMP.
- `scripts/record_demo_headless.sh` — запись демо‑видео без экрана: детектор + RViz2 на виртуальном X‑сервере (Xvfb), бэг в реальном времени, захват ffmpeg. `scripts/compose_demo_video.sh` склеивает ролики с подписями.

> **360° облака (24 МБ на кадр)** при проигрывании с обычного диска: `ros2 bag play` по умолчанию читает вперёд 1000 сообщений (~5 ГБ) и «замирает». Помогает `--read-ahead-queue-size 20`.

## Ограничения

- **Дальность сенсора ≈ 200 м**: возвратов от человека 10 на 150 м, 6 на 175 м, 2 на 200 м, а объект 300 × 300 мм на 200 м меньше ячейки сетки лучей (0.35 × 0.43 м). Поэтому человек обнаруживается до ~150 м; разбор трёх ограничений с графиком — [§ 5.4](docs/experiments.md).
- **На кривых** дальность ограничивает стена тоннеля (прямая видимость 90–150 м). Вне прямой видимости препятствие не видно.
- **Далеко впереди** ось пути восстанавливается по стенам. В широких пространствах (двухпутный тоннель, камеры съездов, станции) она менее точна, поэтому зона там сужается, и обнаружение у самой границы габарита слабее.
- **Низкие объекты** (ниже ~0.3–0.4 м над полом) вдали не отличить от элементов пути.
- **ВНИМАНИЕ** (объект рядом с габаритом) проверяется до 60 м. Дальше неуверенность оси (~0.3 м) не позволяет отличить «рядом с габаритом» от оборудования на стене. ОПАСНОСТЬ проверяется на всей дальности.
- **Смена сечения тоннеля** (прямоугольный → круглый, камеры): смещения стен, измеренные вблизи, дальше не действуют, и ось вдали держится хуже.
